# 派工單（dispatch work orders）

雲端規劃／深審席在這裡落檔，本機總指揮 pull 分支後派工，結果以 commit 回同一分支並在 PR 留言。

## 席位

| 席 | 位置 | 做什麼 | 不做什麼 |
| --- | --- | --- | --- |
| 規劃／深審 | 雲端 session | 出 findings、寫工單、跑驗證、維持 PR Draft | 不推實作 code |
| 總指揮／派工 | 使用者 Windows 本機 | 收工單 → 寫契約 → 派實作 → 跨家族複審 → 合併證據 | — |
| 實作 | Grok（本機艦隊） | 照工單實作 | 不得超出白名單路徑 |

艦隊（Grok / Gemini / Kimi / GLM / MiniMax / Codex）只存在於使用者本機，雲端容器沒有任何線路可以呼叫它們。

## 工單格式

每張工單四段，缺一不可：

1. **標的檔案與函式** —— 明確到檔案與函式／行號，不要寫「相關檔案」
2. **規格（逐條可驗）** —— 每一條都要能單獨判定做到沒有
3. **驗收（測試／突變）** —— 要跑的指令、通過條件，以及**突變驗證**：故意改壞來證明新測試抓得到
4. **可寫路徑白名單** —— 列出允許修改的路徑，其餘一律唯讀

## 共同硬規則

適用於每一張工單，不必重複寫：

- `npm test` 目前 **148 項全綠**。不得刪測試、不得放寬既有斷言來變綠。
- 新增的測試必須**在修正前失敗、修正後通過**。
- 修正要最小。不要順手重構、不要順手改風格。
- 白名單以外的路徑一律不得修改。
- 動到 `src/**` 的工單，交付前要跑 `npm run typecheck`、`npm test`、`npm run soak -- --minutes 2`。

## 已知的過度宣稱（引以為戒）

1. 上一輪的 commit message 寫「`flushDueGroups()` 不再刪除事件建立失敗的 pending group」——
   實際上只擋了 `throw`，沒擋 `insertEvent` 回傳 `false`。WO-006 就是這個洞。
2. 上一輪修 P0-1 只加固了三個 HTTP 伺服器裡的**一個**，而且剛好是唯一預設綁 loopback 的那個。
   另外兩個預設對區網開放的完全沒碰。WO-005 就是這個洞。
3. 上一輪新增 `src/util/image.ts` 是為了修「只看 magic bytes」，但它自己的 PNG 路徑
   在解碼**之後**才檢查像素上限，JPEG 路徑在第一個 SOF 就回傳。WO-012 就是這個洞。

共同教訓：**修一個缺陷時，要先問「同一類的還有幾個地方」**，以及
**宣稱的範圍要等於實際驗證的範圍**。三次都是同一個錯誤模式。
